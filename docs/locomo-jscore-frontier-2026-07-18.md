# LOCOMO holdout: frontier-answerer J-score run

Ordered directly by Rustom: "i need to beat current top locomo score also" /
"yes u can use a better model if need be (dont use api, use from my
subscription)". This run puts memsub on the same measurement axis as the
published competitor numbers in `docs/improvement-plan-2026-07-17.md` Part A
a second way: not just judge-accuracy instead of token-F1 (already done
2026-07-17), but with a **frontier answerer** instead of a local 8B model,
since deviation 1 of `docs/locomo-jscore-2026-07-17.md` named the
local-vs-frontier answerer gap as "by far the largest source of the gap
between memsub's numbers and the competitor numbers." Script:
`scripts/locomo_jscore_frontier_2026-07-18.py`. Raw per-question and
per-condition-summary records, streamed and flushed incrementally, resumable:
`results/locomo-jscore-frontier-2026-07-18.jsonl`.

Executed 2026-07-18, three condition runs (each completed and committed
before the next started), total wall time 3108s + 2858s + 2975s = 8941s
(~149 minutes), none truncated.

## Methodology

Same n=80 LOCOMO holdout slice as both prior J-score runs
(`scripts/holdout_answer_quality.py`'s `holdout_convs()`/`sample()`, LOCOMO
conversations 4-10, `random.Random(123)`, up to 20 questions per category,
category 5 adversarial excluded). Three conditions, run to completion and
committed independently, in priority order:

- `no_memory` -- no retrieved context (floor).
- `naive_topk` -- cosine top-k only, no policy (control: isolates
  memsub-vs-model with the answerer held fixed).
- `graph_decompose` -- memsub's best config as of yesterday
  (`docs/graph-layer-2026-07-18.md`): `HybridSystem.rank_decomposed_graph`,
  the shipped hybrid v2 retriever composed with query-time decomposition and
  the 1-hop entity-graph signal.

**The only variable changed from the prior local-answerer runs is the
answerer.** Per question: the answer is generated by **Sonnet via the local
`claude` CLI** (`claude -p --model sonnet`, Rustom's Max plan subscription,
no API key -- `memsub.backends.ClaudeCLIBackend`), same `ANSWER_SYSTEM`
prompt and same `"CONTEXT:\n...\n\nQUESTION: ..."` structure as every
local-answerer run in this repo, budget 1000 (same greedy-packed context).
`graph_decompose`'s one bounded decompose call (inside
`rank_decomposed_graph`) stays on the **local** qwen3:8b backend, unchanged
from yesterday's run -- retrieval and decomposition are held fixed so this
run isolates the answerer variable specifically, per the task's instruction.
The answer is then graded by a blind Sonnet judge (`memsub/judge.py`, same
judge prompt as both prior runs, sees only question/gold/answer, never the
condition name).

Both the answer-generation and judge `claude` CLI calls are wrapped in a
retrying backend (exponential backoff, base 15s, cap 300s, 6 attempts) to
handle CLI rate limiting gracefully; no retries were needed in practice
during this run (no `answer_error` records; wall times were smooth and
linear throughout).

### Sanity check (first 3 answers, by eye, logged in `WORKLOG.md` before the full run)

1. "What kind of beer does McGee's bar serve?" gold "Stout, lager", Sonnet
   answered "McGee's bar serves stout, lager, and light beers" -- judge
   correctly credited the paraphrase/superset as correct.
2. "How many Prius has Evan owned?" gold "two", Sonnet answered "one" --
   judge correctly marked it incorrect.
3. "What places has Joanna submitted her work to?" gold "film contest, film
   festival", Sonnet answered "I don't know -- the context doesn't specify"
   -- judge correctly marked the non-answer incorrect.

Pipeline confirmed sane (answer format matches protocol, judge tracks gold
vs. answer correctly in both directions) before the full runs.

## Verdict: not yet, and the counter-intuitive result that matters more

**memsub + Sonnet (graph_decompose, 43.75% overall) does not beat mem0's
2025-paper reproduced tier (~61.7% mean) and does not approach Zep's revised
number (75.14%), let alone Dakera/MIRIX/ByteRover/Hindsight.** Say this
plainly, not spun: swapping in a frontier answerer did not put memsub ahead
of the field.

**The more important and genuinely surprising finding: memsub + Sonnet
(43.75%) scored *lower* than memsub + local qwen3:8b on the identical
`graph_decompose` condition and identical n=80 slice measured one day earlier
(51.25%), a 7.5pp drop.** This is the opposite of the expected direction --
the entire premise of this run (and deviation 1 of `docs/locomo-jscore-2026-07-17.md`)
was that a frontier answerer should close most of the gap to competitor
numbers, not open a new one against memsub's own local baseline. This is
reported as measured, not smoothed into a more flattering framing.

### Gap analysis: which categories lose the most (this IS the deliverable)

Comparing Sonnet-graph_decompose to qwen3:8b-graph_decompose, category by
category:

| category | qwen3:8b (07-18) | Sonnet (this run) | delta |
|---|---|---|---|
| multi-hop | 50.0% | 45.0% | -5.0pp |
| temporal | 35.0% | 25.0% | **-10.0pp** |
| open-domain | 40.0% | 35.0% | -5.0pp |
| single-hop | 80.0% | 70.0% | **-10.0pp** |

The two categories that dropped the most switching to Sonnet -- **temporal
and single-hop** -- are not the "hard reasoning" categories (multi-hop) one
might expect a stronger model to help most and lose least on. Multi-hop and
open-domain dropped a smaller, more ordinary-looking 5pp each. Temporal and
single-hop, categories where a confident short factual guess is often
enough to satisfy the judge, dropped twice as much.

**Working hypothesis, stated as a hypothesis, not proven by this run**:
Sonnet follows `ANSWER_SYSTEM`'s explicit instruction ("If CONTEXT does not
contain the answer, say you don't know rather than guessing") far more
faithfully than qwen3:8b does. The sanity-check answers above show this
directly -- Sonnet declined outright on question 3 rather than guess. A
weaker local model appears to guess more readily even when the retrieved
context is thin, and an LLM judge grading on "does the answer capture the
gold fact, in any phrasing" gives no credit for calibrated uncertainty --
a confident wrong-ish guess and an honest refusal are both scored
INCORRECT, but only the refusal is guaranteed to score that way, while a
guess has some chance of accidentally landing on the gold fact (especially
on temporal and single-hop questions, which tend to have short, low-entropy
gold answers a plausible guess can hit). This would explain why the
category losses concentrate exactly where guessing is cheapest to get right
by chance, not where reasoning is hardest. This hypothesis is not verified
here (would require, e.g., re-running with a less conservative answer
prompt, or auditing how many of Sonnet's "false" verdicts are outright
refusals vs. wrong guesses) -- flagged as the natural next measurement, not
claimed as settled.

### The positive signal underneath the negative headline: memsub's relative lift held up, even grew

Isolating the answerer from the retrieval question (compare each answerer to
its own `naive_topk` control):

- **Local (qwen3:8b)**: naive_topk 37.50% -> graph_decompose 51.25%
  (07-17/07-18, cross-run pooled since local naive_topk was not re-measured
  on 07-18) = **+13.75pp**.
- **Frontier (Sonnet)**: naive_topk 27.50% -> graph_decompose 43.75%,
  same-run, same day = **+16.25pp**.

memsub's contribution over naive top-k retrieval, with the answerer model
held fixed, is *proportionally larger* with the frontier answerer than with
the local one (+16.25pp vs +13.75pp). Relative to the floor, the picture is
mixed and reported honestly rather than picked for flattery: Sonnet's
no_memory (3.90%) to graph_decompose (43.75%) is a +39.85pp / 11.2x lift,
versus local's no_memory (2.53%) to graph_decompose (51.25%), a larger
+48.72pp / 20.3x lift -- local's lift off the floor is bigger in both
absolute and multiplicative terms, the opposite direction from the
naive_topk-relative comparison above. Taken together: **memsub is not the
thing losing the most ground when the answerer gets stronger** -- naive_topk
dropped by 10pp (37.50% -> 27.50%) and no_memory dropped by a smaller
absolute amount but stayed near-zero in both cases, so the drop is present
across all three conditions, not concentrated in memsub's own retrieval
contribution. But the two lift framings do not agree on direction, and
that disagreement itself is worth flagging rather than resolving by
choosing whichever framing looks better.

### Single-hop and multi-hop specifically beat mem0's reproduced tier; temporal and open-domain do not

The most apples-to-apples-ish external comparison is mem0's 2025 paper
(GPT-4o-mini, independently reproduced), since it is the only competitor
number in the table with a full per-category breakdown and the smallest
answerer-tier gap to Sonnet:

| category | memsub + Sonnet | mem0 (GPT-4o-mini, reproduced) | delta |
|---|---|---|---|
| single-hop | **70.0%** | 67.1% | **+2.9pp, memsub ahead** |
| multi-hop | 45.0% | 51.2% | -6.2pp |
| temporal | 25.0% | 55.5% | -30.5pp |
| open-domain | 35.0% | 72.9% | -37.9pp |

memsub + Sonnet's single-hop number edges mem0's reproduced single-hop
number, and multi-hop is within a single-run n=20 noise band (-6.2pp is
about 1 question at this n). **Open-domain and temporal are where the real
gap lives, not multi-hop** -- the opposite of what
`docs/improvement-plan-2026-07-17.md`'s framing ("the real gap: multi-hop")
predicted before this run. Temporal is plausibly explained by memsub having
no dedicated temporal-reasoning structure (no dual timestamps the way Zep's
graph has, per Part A); open-domain's -37.9pp gap is the largest in the
table and the most concerning, worth its own follow-up investigation before
the next round of work.

## Honest deviations from the official LOCOMO J-score protocol

Everything already stated in `docs/locomo-jscore-2026-07-17.md`'s deviations
1-4 (n=80 slice not full set, single run no variance estimate, memsub is a
retrieval layer not an end-to-end product) still applies. New/updated for
this run specifically:

1. **Judge model family is now the same family as the answerer.** Both the
   answerer and the judge are Sonnet via the `claude` CLI. Published LOCOMO
   numbers typically use GPT-4o/4.1-class judges over GPT-4o/4.1-class
   answerers (same-family pairing), so this is not a new asymmetry relative
   to competitors, but it does mean any Sonnet-specific answer style (see
   hedging hypothesis above) is being graded by a judge from the same model
   family, which could compound rather than cancel out.
2. **Competitor answerers are GPT-4o-mini / gpt-4.1-mini class, smaller and
   cheaper than Sonnet.** "Frontier" is not one tier -- Sonnet is a larger,
   more capable, more expensive-class model than the mini-tier models most
   competitor numbers were produced with. This makes the comparison closer
   in spirit (both frontier-class, not local-vs-cloud) but not identical in
   raw capability.
3. **Retrieval and decomposition stayed on the local qwen3:8b backend even
   in the frontier-answerer conditions**, by deliberate design, to isolate
   the answerer as the single changed variable per the task's instruction.
   This is not a fully "frontier end-to-end" measurement -- a pipeline where
   Sonnet also did the decomposition might score differently (untested,
   out of scope for this run's budget).
4. **`ANSWER_SYSTEM`'s explicit "say you don't know" instruction was carried
   over unchanged from the local-answerer protocol.** This prompt was
   designed and never tuned against qwen3:8b's behavior; how a frontier
   model responds to the same instruction is exactly the mechanism flagged
   above as the likely driver of the counter-intuitive result. Competitors'
   own answer prompts are not published, so it is unknown whether they use
   a comparably conservative instruction.
5. **`graph_decompose` was carried over as memsub's best config from the
   local-answerer eval without re-selecting a best config for Sonnet
   specifically.** It is possible a different memsub configuration (e.g.
   plain `memsub_hybrid_v2` without decomposition, or `naive_topk` with a
   different budget) would score differently paired with Sonnet -- not
   tested here.
6. **Malformed judge counts differ by condition and run**: this run's
   `no_memory` had 3/80 malformed judge responses (n_ok=77); `naive_topk`
   and `graph_decompose` were clean (n=80 each). All excluded from accuracy
   rather than guessed, per `memsub/judge.py`'s policy, consistent with
   every other run in this repo.

## Honest claim language for future reference

Say: "memsub, evaluated with a frontier answerer (Sonnet via the `claude`
CLI, Rustom's subscription, no API key) instead of a local 8B model, scores
43.75% overall J-score accuracy on the same n=80 LOCOMO holdout slice
(graph_decompose config) -- lower than memsub's own local-answerer result on
the identical condition (51.25%) the day before, and lower than every
quoted frontier-answerer competitor number in this table. memsub's
single-hop number (70.0%) edges mem0's reproduced single-hop number
(67.1%), and multi-hop (45.0% vs 51.2%) is within single-run noise; temporal
and open-domain carry the real gap (-30.5pp and -37.9pp against mem0). The
counter-intuitive local-vs-frontier drop is not fully explained by this run
-- the leading hypothesis is that a frontier model follows the 'say you
don't know' instruction more faithfully than a local model does, which an
LLM judge does not reward relative to a lucky guess -- flagged as a
hypothesis for the next measurement, not a settled finding."

Do not say: "memsub beats mem0" or "frontier answerer confirms memsub is
competitive" -- neither is true on this evidence. Do not smooth over the
qwen3:8b > Sonnet result on the same condition; it is the most informative
single number this run produced.
