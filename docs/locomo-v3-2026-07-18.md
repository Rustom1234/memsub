## Item 1: v3 combined run (best-effort prompt + date surfacing together)

Both fixes existed in `scripts/locomo_jscore_frontier_2026-07-18.py` from
round 2 but had never been run together on the full n=80 slice --
round 2's Task 3 only exercised `--with-dates` on the temporal category in
isolation (n=20) and flagged the combined number as an untested arithmetic
extrapolation. This run measures it directly.

`--condition graph_decompose --prompt best_effort --with-dates`, n=80 (same
holdout slice as every prior round: LOCOMO conversations 4-10,
`random.Random(123)`, up to 20 per category), Sonnet answerer + Sonnet
judge via the `claude` CLI (subscription, no API key), budget 1000 (the
existing default). Streamed to `results/locomo-jscore-v3-2026-07-18.jsonl`.
Wall time 3366s (~56 min), zero retries/errors, 80/80 judged ok.

| metric | v2 (best-effort only) | **v3 (best-effort + dates)** | delta |
|---|---|---|---|
| overall | 52.5% | **56.25%** | **+3.75pp** |
| multi-hop | 45.0% | 45.0% | +0.0pp |
| temporal | 30.0% | 45.0% | **+15.0pp** |
| open-domain | 50.0% | 55.0% | +5.0pp |
| single-hop | 85.0% | 80.0% | -5.0pp |

The combined 56.25% lands almost exactly on round 2's flagged extrapolation
`(45+45+50+85)/4 = 56.25%` -- now an actually measured single end-to-end
run rather than arithmetic. Temporal's +15.0pp matches round 2's isolated
n=20 temporal-only measurement exactly, confirming that isolated result
generalizes cleanly to the full combined run with no interaction penalty.
Open-domain picked up a small bonus (+5.0pp, plausibly some open-domain
questions also carry a temporal element the date prefix resolves).
Single-hop dipped -5.0pp (one question's worth of noise on n=20 -- not
investigated further, out of Wave 1 scope).

## Item 2: packed-context budget ablation

Same condition (`graph_decompose`), same slice, same v3 prompt+dates
config -- only `--budget` changes (new flag added to the eval script this
round; default remains 1000, unaffected for every other caller). Budget
1000 reuses item 1's run above (no separate execution). Budgets 2000 and
4000 each streamed to their own file (`-b2000`/`-b4000` suffix), same
wall-clock shape (~56-57 min each), zero retries/errors, 80/80 judged ok
in both.

| budget | overall | multi-hop | temporal | open-domain | single-hop |
|---|---|---|---|---|---|
| 1000 (item 1's v3) | 56.25% | 45.0% | 45.0% | 55.0% | 80.0% |
| **2000** | **63.75%** | 50.0% | **70.0%** | 55.0% | 80.0% |
| 4000 | 62.5% | 55.0% | 65.0% | 50.0% | 80.0% |

**Budget 2000 wins materially over 1000 (+7.5pp, well past the 2pp bar) and
is the best of the three** -- 4000 does not buy further gain (-1.25pp vs
2000; open-domain actually drops below even the budget-1000 number at
4000, 50.0% vs 55.0%, plausibly more low-relevance context diluting the
greedy pack at the highest budget). Temporal is the biggest mover across
budgets (45% -> 70% -> 65%), consistent with round 2's diagnosis that more
budget room means more of the evidence turns carrying the crucial
session-date anchor actually fit alongside the relative-date phrase they
resolve.

**Token cost, stated honestly**: budget 2000 roughly doubles the packed
context per question versus budget 1000 (the hard cap that bounds how much
episode content is stuffed into the prompt). Because the answerer and judge
run through the `claude` CLI on Rustom's Max plan subscription (never a
metered API key), there is no dollar-per-token cost to report -- the real
cost is prompt-window usage against the subscription's own limits, not
cash. Wall-clock and mean per-question latency were flat across all three
budgets (~17.3-17.6s mean answer latency, ~17.3-17.9s mean judge latency) --
the dominant cost is generation time, not context-ingestion time, at these
budget sizes.

**Per item 2's stated rule ("if a higher budget wins materially, it becomes
the new eval default going forward"): budget 2000 is the new recommended
default for this frontier eval going forward**, noted here rather than
silently changed in `scripts/metrics_local.py`'s shared `BUDGET = 1000`
constant -- that constant is the frozen, already-published budget for many
other historical evals in this repo (graph-layer eval, multihop evals,
etc.), and silently repointing it would misrepresent those numbers'
reproducibility. Future frontier-eval runs of this script should pass
`--budget 2000` explicitly.

## Item 3: date surfacing productized

`memsub.store.format_episode(ep, with_dates=False)` -- the single shared
implementation of the `[session_date] content` formatting rule, default
False (returns `ep.content` unchanged, byte-identical to before this flag
existed). `memsub.sdk.MemoryClient.inject(..., with_dates=False)` now
exposes it as a real opt-in SDK parameter (the actual production entry
point: `from memsub.sdk import MemoryClient; client.inject(...)`), not
`memsub/memory.py`'s separate, older `ContextStuffingMemory`/
`RetrievalMemory` concept-log harness, which is not wired to the
benchmarked v2 `HybridRetriever` stack or used by any eval in this repo.
`scripts/locomo_jscore_frontier_2026-07-18.py`'s local `_format_episode`
hack is gone -- it now imports and calls the same library function, so the
eval path and the SDK path are provably identical, not two copies that can
drift.

Unit tests (`tests/test_sdk_mcp.py`): `format_episode` default-off is
byte-identical to `ep.content`; `with_dates=True` prefixes the session date
when present and falls back to plain content when absent;
`MemoryClient.inject(with_dates=False)` (both explicit and the method's own
default) is byte-identical to `inject()` before this flag existed;
`inject(with_dates=True)` surfaces the dated prefix. All 5 new tests green,
part of the 319-passed suite total.
