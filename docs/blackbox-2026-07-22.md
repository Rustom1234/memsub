## What it does

Blackbox is a product layer over memsub/filehist.py's flight recorder.
Coding-agent transcripts already contain a full history of every file
write/edit/read an agent ever performed. Blackbox indexes that history
incrementally into a local SQLite table, then:

- **`memsub blackbox scan [--root DIR]`** (default root `~/projects`):
  discovers git repos under root, indexes every known transcript/history
  source (Claude Code, Codex CLI, Cursor, Aider), then checks every
  discovered repo's tracked files against the index. Prints CLEAN, or
  names each file that has silently regressed to an older known state,
  with the exact restore command. Read-only: scan never writes to a repo.
- **`memsub blackbox restore <file> [--at TIMESTAMP]`**: writes a file's
  reconstructed content back to disk, as of a given moment (ISO 8601 or
  `YYYY-MM-DD HH:MM`) or the latest known state if `--at` is omitted.
- **`memsub blackbox status`**: index size, when the index was last swept,
  and a fresh disk recheck (no re-indexing).
- Standalone `blackbox` console script (`pyproject.toml`
  `[project.scripts]`): `blackbox scan` / `restore` / `status` are exactly
  `memsub blackbox scan` / `restore` / `status`; `memsub/blackbox.py:main`
  is a one-line passthrough into the same argparse parser cli.py owns, so
  there is exactly one place that owns these commands' arguments.

All three new parsers are wired into `blackbox scan`'s discovery path
behind the Claude Code parser (`memsub/blackbox.py:scan`), and each is
individually guarded: the tool's directory/database being absent is a
silent no-op (returns 0), never an error, never a slowdown.

## Does NOT do (known limitations, on the record)

- **Rollback detection fires only on exact snapshot match.** A file that
  rolled back and was then hand-edited (diverged further) is invisible to
  `check_rollbacks`; only a dependent import breaking would surface it.
  Same limitation as documented in `docs/research-memory-landscape-2026-07-21.md`.
- **Codex CLI's JSONL schema is unverified.** No real `~/.codex` directory
  or Codex install was available on this machine to inspect. The parser is
  built from Codex's own long-stable `apply_patch` text convention, not a
  captured transcript; if Codex's actual event envelope differs from the
  guessed shape, the parser finds nothing (fails open, never crashes) but
  also indexes nothing useful.
- **Codex "Update File" patches are coarse.** All removed lines in one
  hunk are joined into one `old_string`, all added lines into one
  `new_string`. A hunk with more than one separate change loses the
  ordering between those changes and may not replay byte-exactly through
  `filehist.reconstruct`. Only "Add File" patches (full new content) are
  byte-exact.
- **Cursor parser is fixture-tested only.** No real Cursor install exists
  on this machine. Table/key layout (`ItemTable`/`cursorDiskKV`,
  `composerData:*`/`bubbleId:*`) is community reverse engineering, not
  documented by Cursor; the JSON field names this parser looks for inside
  a value (`codeBlocks`, `uri.path`/`path`, `content`) are a best guess. A
  real database with different field names yields 0 rows, silently.
- **Cursor indexing has no byte-offset checkpoint.** Its sqlite store is a
  live key-value store, not an append-only log, so every scan rereads the
  whole database; a per-row `(path, transcript, content_hash)` check keeps
  reruns from duplicating rows, at the cost of one SELECT per row every
  scan.
- **`restore` is manual, not automatic.** `scan` only reports; nothing is
  ever written to disk unless a human (or a script) explicitly runs
  `blackbox restore`.
- **No pre-restore backup.** `restore` overwrites the target file with the
  reconstructed content. If the file's current on-disk content isn't
  itself already a known state in the index, it is not separately saved
  before being overwritten.
- **Repo discovery does not descend past a found `.git`.** A repo nested
  inside another already-discovered repo (e.g. a worktree under
  `.claude/worktrees/`) is not scanned as its own entry; this avoids
  double-scanning worktrees but means a genuinely separate nested repo a
  user manages by hand could be missed.
- **The 40 incidents found on this machine during the measured run above
  were not triaged or restored** as part of this build; they belong to
  repos (airthrow, book-dna, memory-sublayer's own working tree) outside
  this task's scope, and `blackbox restore` was deliberately not run
  against them.

## Standalone install (2026-07-22 addendum)

`scripts/blackbox-install.sh` is the one-command install a stranger runs.
It picks an isolated-tool installer in order of preference (uv, then pipx,
then a `pip --user` venv), installs the package so `blackbox` is on PATH
with no repo or venv activation, and then runs `blackbox scan` immediately
so the first thing the user sees is either CLEAN or their own lost work.
Set `BLACKBOX_ASSUME_YES=1` to skip the uv-bootstrap prompt in unattended
installs. It never touches the user's code and makes no network calls
beyond fetching the installer/package.

Known packaging caveat, on the record: the `blackbox` console script still
imports the full `memsub` CLI parser, so `uv tool install` pulls the whole
memsub package (and numpy) even though the flight-recorder code path itself
is stdlib + sqlite only. Decoupling the standalone entry point from
`cli.build_parser` so a flight-recorder-only install is lean is a deferred
refactor, not done here.

## Scan defaults broadened (2026-07-22 addendum)

The first-run scan now looks beyond `~/projects`. Repo roots default to the
common developer code dirs that exist (`~/projects`, `~/code`, `~/src`,
`~/dev`, `~/repos`, `~/work`, `~/Documents/GitHub`, `~/git`, `~/go/src`)
plus the current directory, and transcript sources include the standard
Claude Code home, the isolated remote-control home, and the XDG config
home. Repos are deduplicated by resolved path (overlapping roots and cwd),
and a directory the user cannot stat (for example `/tmp` systemd-private
dirs reached via cwd) is skipped rather than aborting the scan.

## A real false positive, for honesty

Running the broadened scan from a fresh index on this machine flagged two
files inside memory-sublayer's own tree (`tests/test_daily_extract.py`,
`tests/test_sleep_cli.py`) as "recoverable loss": their current disk
content byte-matches an older transcript snapshot while a newer, different
snapshot also exists in the transcripts. Both files are at committed HEAD
and their tests pass, so the current content is correct: the newer
transcript state was an intermediate that was later intentionally
superseded. This is exactly the documented limitation (detection fires on
exact match to an older known snapshot and cannot tell an intentional
revert from a silent rollback). The fix is to look before you restore;
`restore` was not run against these.
