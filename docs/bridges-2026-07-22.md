# Bridges: non-obvious connections between projects (2026-07-22)

A gift feature: mine the owner's own memory store for pairs of memories
that live in different projects, are similar enough to be worth a look, and
were never linked, deduped, or retrieved together by anything else in
memsub. Not a new memory source, not a new store -- a read pass over the
existing episodic store, plus a small JSON cache for verdicts.

## What it does

- **`memsub bridges scan [--json] [--db PATH] [--cache PATH] [--k N] [--embedder hashing|ollama|auto] [--no-llm]`**
  runs `memsub.bridges.find_bridges` against the active episode set, merges
  the result with any cached keep/dismiss verdicts, adds an ollama why-line
  to the top 20 when a local daemon is reachable, and prints the result
  (plain text, or `--json` for machine output).
- **`memsub bridges serve [--port 8768] [--db PATH] [--cache PATH]`** is a
  stdlib-only HTTP server, same house style as `memsub vault serve`: dark,
  phone-first, no frameworks, no third-party JS. It computes bridges once at
  startup (or reuses whatever `scan` already cached), then serves a
  "constellation" page: one card per bridge, the two memory excerpts side by
  side, their bucket chips, the why-line when present, a similarity-strength
  bar, and keep/dismiss buttons. Filter chips (one per bucket pair) narrow
  the grid client-side. `POST /api/verdict` records a keep or dismiss,
  updates the in-memory list, and persists it to the cache file -- visible
  on the next load without a restart.

## How a bridge is found (`memsub/bridges.py:find_bridges`)

1. Every active episode is embedded with the store's embedder (hashing by
   default, zero dependencies; `--embedder ollama`/`auto` for real local
   embeddings when a daemon is reachable) and every pair's cosine similarity
   is computed, the same full pairwise-matrix approach
   `memsub.consolidate.consolidate` already uses for dedup at this scale.
2. Each episode is assigned a **bucket**, in this order:
   1. an explicit project hint parsed from `provenance["source"]`'s
      directory segment (the transcript's project folder, e.g.
      `.../-homes-x-projects-book-dna/s.jsonl` -> `book-dna`)
   2. failing that, its strongest (highest-degree) entity from the graph
      tables (`memsub.graph`), if that layer has been populated for this
      store
   3. failing both, a prefix of its session id
3. A pair is excluded when it is: from the **same bucket**; a **near-dup**
   (cosine >= `memsub.consolidate.ConsolidationConfig.dedup_threshold`,
   0.92 by default); **entity-linked** (the two episodes share at least one
   `entity_links` row); or **co-retrieved** (both ever appear in a
   "retrieved" event carrying the same query string -- the store has no
   explicit per-recall id, so this is the closest available proxy for "the
   retrieval stack already surfaced these two together").
4. Surviving pairs score `similarity * cross_bucket_bonus`, where the bonus
   is an inverse-sqrt weight on how often that exact bucket pair recurs
   among this run's surviving candidates -- a bridge between two projects
   that rarely pair up outranks an equally-similar bridge between two that
   constantly do. Top `k` (default 50) are returned, highest score first.

## Persistence

Bridges and verdicts are cached as one JSON file, default
`~/.memsub/bridges.json` (override with `--cache` on both commands, or the
`cache_path` parameter in code; tests never touch the real path). A
`"dismiss"` verdict removes a pair permanently from every future run;
`"keep"` pins it to the top. The cache never stores anything not already
computable from the store -- deleting it just means the next `scan` starts
cold.

## Does NOT do

- **The hashing embedder is crude.** It is a hashed bag of word-unigrams
  and character-trigrams (`memsub/embed.py:HashingEmbedder`), not a trained
  semantic model. It catches shared vocabulary, not shared meaning across
  differently-worded ideas; `--embedder ollama`/`auto` (a real local
  embedding model) finds more, and finds them better, but is not the
  default because it needs a daemon running.
- **Buckets are a heuristic, not ground truth.** The project-hint parser
  guesses a project name from a transcript folder's naming convention; the
  entity-cluster fallback only fires when `memsub graph backfill` has been
  run; the session-id fallback is a last resort with no project meaning at
  all. Two memories can share a "bucket" string for reasons that have
  nothing to do with the person's actual mental model of their projects.
- **The co-retrieval exclusion is a proxy, not an audit trail.** The event
  log records a query string per retrieval, not a recall-session id, so
  two unrelated recalls that happened to use the exact same query text
  would look "co-retrieved" here. In practice this only ever makes the
  filter slightly more conservative (a few more pairs excluded than
  strictly necessary), never less.
- **This finds candidates worth a human look, never verified truths.** The
  score is a similarity-times-rarity number, not a confidence that a real
  connection exists. The optional why-line is a local LLM's one-sentence
  guess, generated from two short excerpts with no other context -- treat
  it as a prompt for the person's own judgment, not an explanation.
- **No write path into the episodic store.** Nothing here appends,
  supersedes, or forgets a memory; the only file this feature ever writes
  is the bridges/verdicts cache.
