# Belief-revision ripple: impact analysis for your memories (2026-07-20)

Ordered directly: the product's hero feature. Read first for design and
assumptions: `WORKLOG.md` 2026-07-20 "Belief-revision ripple engine" (the
Karpathy-rule plan, written before any code). File boundary this round: new
`memsub/ripple.py`, `tests/test_ripple.py`, `scripts/ripple_demo.py`, this
doc, `WORKLOG.md`. UI wiring is a later pass -- this round builds the engine
and makes it callable.

## The pitch

Every memory system lets you correct a fact. None of them tell you what that
correction touches. When you fix a belief in memsub, the old fact may have
already been folded into a fusion summary, cited as a source in a distilled
topic note, or chained through a run of duplicate-collapse decisions -- all
of that downstream state still reflects the thing you just decided was
wrong, and nothing surfaces it. `memsub.ripple` is impact analysis for your
beliefs: point it at a memory and it answers "changing your mind about this
touches these N things," with a plain-English explanation of exactly how
each one connects back, grouped from strongest evidence to weakest. This is
the demo hero because it is the one thing no other personal-memory tool
shows you.

## What it computes

`ripple(store, memory_id, max_hops=2)` walks four derivation-edge tiers,
strongest to weakest:

1. **Fusion** -- a `fused_into` event on the memory (`memsub.consolidate`
   phase 3): a fusion episode was built citing this memory as a source.
2. **Topic membership** -- a distilled topic note (`memsub/distill.py`)
   lists this memory as a member, cited by wikilink in its machine-generated
   block.
3. **Supersede chains, both directions** -- this memory superseded
   something (it's the winner), or was itself superseded by something (it's
   the loser) -- consolidation dedup/contradiction decisions or a human
   correction.
4. **Associative** -- entity-share neighbors, weighted by how many entities
   they have in common with the root memory.

Tiers 1-3 are walked breadth-first up to `max_hops` and grouped into
`derived_directly` (hop 1) and `derived_transitively` (hop >= 2). Tier 4 is
computed once from the root memory only, capped to the top 10 neighbors, and
reported separately as `associatively_related` -- it never chains across
hops and never gets promoted into a "derived" tier.

Each affected item carries: a prose title (first sentence of its content,
never a slug or id), a type (`memory` / `fused` / `topic` / `idea`), the
tier it landed in, a plain-words path explaining how it connects back to the
root (e.g. `superseded by "..." (reason: human_correction)`, `cited as a
source in fused entry "..."`), and an impact score. Impact score is
tier-weighted (`derived_directly`=3.0, `derived_transitively`=1.5,
`associatively_related`=0.5 x shared-entity count); a report's
`total_impact_score` is the sum, so "count-weighted by tier" holds at both
the item and the report level.

`ripple_on_event(store, event)` is a one-line wrapper keyed on
`event.episode_id` -- the entry point future event wiring (a supersede,
reject, or correction happening live) will call directly, since
`memsub/store.py` always logs a lifecycle event against the affected
(loser) episode's id.

The whole module is pure graph walking over indexes `memsub/store.py` and
`memsub/graph.py` already maintain, plus a read-only regex scan of
`vault/topics/*.md`. Zero LLM calls. Measured ~30-35ms against the real
~5.4k-episode / ~2.6k-event live store, well under the 100ms target.
`RippleReport.to_dict()` is plain dicts/lists/strings/numbers -- drop it
straight into a UI panel's JSON response.

## Honest limits

- **The associative tier is correlation, not derivation.** Two memories
  sharing an entity does not mean either one caused, cited, or built on the
  other -- it means they were both tagged with the same rule-based entity
  extractor. It is deliberately the weakest-weighted tier, deliberately
  root-only (never chained across hops, so it cannot masquerade as a
  multi-hop derivation path), and every explanation string it produces says
  "associative, not derivation" out loud rather than implying causality.
- **Topic-note membership depends on distillation having run.** The live
  vault (`~/memsub-vault`) has no `topics/` directory yet as of this build
  (Layer 1 distillation, `docs/second-brain-spec-2026-07-20.md`, has not
  been run against the real store) -- the topic-membership tier is fully
  exercised by unit tests against a synthetic vault and will start
  surfacing real hits the first time `memsub distill` runs. `ripple()`
  degrades cleanly (empty topic tier, no error) when the vault or its
  `topics/` folder is missing.
- **Supersede-chain depth is bounded by real consolidation history, not by
  design.** The longest real chain found in the live store's audit trail is
  6 hops; `max_hops=2` (the default) only shows the first 2. Callers who
  want the full chain can raise `max_hops`, at the cost of walking further.
- **No cross-namespace guardrail beyond what the store already provides.**
  `ripple()` walks whatever ids the store's edges point to; it does not
  re-check namespace boundaries itself (the write paths that create those
  edges -- fusion, supersede, entity linking -- are namespace-aware
  already, so this has not been an issue in practice, but it is not
  independently enforced here).

## Three real cases (live store, `scripts/ripple_demo.py`)

Found by querying the live store's audit trail directly
(`memory_events` where `event='superseded'`/`'fused_into'`), not invented.

| Case | memory_id | status | tiers hit | total impact |
|---|---|---|---|---|
| 1. Human correction (OpenClaw attribution) | `0054af9952a9...` | superseded | derived_directly (1) | 3.0 |
| 2. Duplicate-collapse chain | `bf35552fec52...` | superseded | derived_directly (1), derived_transitively (1) | 4.5 |
| 3. Fusion source + rich associative neighborhood | `cf4855a8f9ab...` | active | derived_directly (1), associatively_related (10) | 8.0 |

**Case 1** is the one the task brief named: a fact that implied Rustom built
OpenClaw as his own project ("...using LangChain, OpenClaw, OpenAI...") was
corrected to remove OpenClaw from his personal ML experience -- the only
`human_correction` event in the store, not an automatic dedup decision. It
is a small, clean, one-hop ripple: exactly one derived item, the corrected
replacement fact.

**Case 2** is a 7-copy duplicate of near-identical "builds applied LLM and
agent systems ... using LangChain, OpenClaw, ..." wording that consolidation
collapsed one hop at a time; ripple on the first loser in that chain reaches
2 hops deep at `max_hops=2` (the chain itself runs 6 hops in the full audit
trail).

**Case 3** is the richest: an ILS-optimization fact was folded into a
fusion note (`derived_directly`) and separately shares entities with 10
other memories about the same optimization work (`associatively_related`,
capped at the top 10) -- the only one of the three that lights up two tiers
at once.

    [memory] Rustom has experience as an ML engineer working with PyTorch, TensorFlow, LangChain, OpenA...  (impact 3.0, status: active)

    (none)

Run `python3 scripts/ripple_demo.py` from the repo root (with `PYTHONPATH=.`
or the project's venv active) to reproduce all 3 reports against the live
store.
