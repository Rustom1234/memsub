# Dogfood run, 2026-07-12: real Claude Code transcripts through extract -> consolidate -> vault sync

Acceptance test for the Obsidian vault layer (docs/obsidian-layer.md,
memory-sublayer-dg5): run the real pipeline over Rustom's own Claude Code
session transcripts and produce a vault he can open in Obsidian today. All
numbers below are from the actual run, logged to `/tmp/dogfood_extract.log`
and `/tmp/dogfood_consolidate.log` during the run. Nothing here is
estimated or fabricated.

This doc deliberately does not quote any extracted memory content or vault
note filenames (filenames are content-derived slugs): per the task rules,
transcript-derived content stays local, not in the repo. Source transcript
file *paths* below are just filesystem locations under
`/home/user/.claude/projects/`, not conversation content.

## What was ingested

`/home/user/.claude/projects/` holds 3,569 `.jsonl` session files, 479MB
total, across 24 project directories. That is too much to run unattended
through an LLM in one sitting, so this run samples deliberately.

Sampling method: a random size-filtered scan (400 candidate files, excluding
`subagents/` and `tool-results/` subpaths, 2KB-1.5MB) measured real
(`user`/`assistant`) turn counts per session using memsub's own
`load_transcript`. Finding worth stating honestly: the **median** session in
this corpus has only 2 real turns after filtering out hook/attachment/queue
noise (many `.jsonl` files are single-shot automation runs, not
conversations). From that scan:

- 8 substantive multi-turn sessions (4-37 real turns each) were picked,
  capped at 2 per project directory, spanning 6 distinct project
  directories.
- 6 typical short (2-turn) sessions were picked from the memory-sublayer
  project's own transcript history, since this tool's own development is
  the most relevant dogfood material.

14 files total, 176 real turns, 89,312 characters of actual message text
(3.08MB of raw file bytes on disk; the gap is tool-result/attachment JSON
that `extraction.load_transcript` correctly filters out before anything
reaches the LLM).

## Pipeline run

Backend: `ollama` (`qwen3:8b`), the local model already pulled on this
machine. Namespace: `claude-code`. Run id: `dogfood-2026-07-12`.

| Stage | Command | Wall time | Result |
|---|---|---|---|
| Extract | `memsub extract <file> --backend ollama --namespace claude-code --run-id dogfood-2026-07-12` x14 | 200s total (14.3s/file avg) | 57 memories written; 3 of 14 files produced zero candidates |
| Consolidate | `memsub consolidate --namespace claude-code --backend ollama` | 11s | 0 actions (0 dedup, 0 contradiction, 0 decay); 57 active memories remain |
| Vault sync | `memsub vault sync --vault /home/user/memsub-vault` | 1s | 57 written, 0 updated, 0 unchanged, 0 removed |
| Vault sync (rerun, no store changes) | same command | 1s | 0 written, 0 updated, 57 unchanged, 0 removed |

Memory kind breakdown from extraction: 35 fact, 11 event, 8 decision, 3
preference. Average memory content length: 129 characters. Store file:
`~/.memsub/memory.db`, 72KB. Vault: `/home/user/memsub-vault`, 256KB,
57 notes + 2 index notes (1 namespace index + 1 top-level MOC), outside any
git repository (verified with `git rev-parse --is-inside-work-tree` from
`/home/user`, which fails as expected).

## Consolidation: 0 actions, and why that is expected, not broken

The sample spans 14 topically unrelated sessions (six different projects,
no repeated facts), so there was nothing to dedup or contradict. Decay
requires `decay_min_age_days=14` by default and every memory in this run
was written seconds before consolidation ran, so the decay phase
structurally skipped all 57. This means the real run did not exercise the
"superseded memory links forward" vault behavior end to end on real data;
that path is covered instead by `tests/test_vault.py::
test_superseded_memory_links_forward_and_stays_in_vault` (synthetic
supersede event, asserts both the forward and backward wikilink render). A
real supersede/contradiction chain would only show up dogfooding again
after two or more weeks of overlapping, evolving memories, which is a
finding in itself: a same-day dogfood run cannot exercise consolidation's
main value prop.

## Verification performed

- All 57 note files' YAML frontmatter parses with `yaml.safe_load` (checked
  programmatically against every `.md` file in the vault except the two
  frontmatter-free index notes, which is correct: they are indexes, not
  memories).
- Every `[[wiki-link]]` in the vault (both note-to-note links and the MOC's
  namespace links) resolves to a file that exists in the vault: 0 broken
  links found by a full-vault regex + filesystem check.
- 18 of the 57 notes carry at least one "shares entity" link; entities
  found include names, tool names, and project terms recurring across
  otherwise-unrelated sessions.
- Namespace index (`claude-code/index.md`) groups all 57 notes by kind with
  correct counts (fact 35 / event 11 / decision 8 / preference 3), matching
  the CLI's own reported extraction totals.
- Top-level MOC (`index.md`) lists the one namespace present with a count
  of 57, matching the store.
- Manually opened and read 3 individual notes plus both index notes;
  frontmatter, provenance (source path, session id, generation time,
  backend/model, turn span), and the Links section all rendered as
  designed. (Content excerpts were relayed directly to Rustom, not
  committed here — see "what was ingested" above for why.)

## UX friction (honest findings, not all fixed)

1. **`--db` placement is easy to get wrong.** `memsub vault` follows the
   existing `ns` command's convention (`--db` on the parent parser, before
   the subcommand): `memsub vault --db PATH sync --vault DIR`, not
   `memsub vault sync --db PATH --vault DIR`. Consistent with the codebase,
   but non-obvious on first use; hit this while writing the CLI tests.
2. **No batch/glob extract.** `memsub extract` takes exactly one file.
   Running this dogfood sample meant a shell loop over 14 paths one at a
   time. Fine at 14 files; would be real friction at the scale this corpus
   actually is (3,569 files). Not fixed here (out of scope for this task),
   flagged as a real gap for anyone who wants to ingest their full
   transcript history in one command.
3. **Extraction over hook/automation-only sessions correctly returns
   nothing.** 3 of 14 sampled files produced "no candidate memories
   extracted." That is the extractor working as designed (nothing durable
   was said), not a failure, but it means naive "extract everything" over
   this corpus would spend real LLM time on a lot of near-empty sessions
   given the median-2-turns finding above.
4. **Extraction quality, positive finding.** The 57 memories read as
   specific and durable (infrastructure details, decisions with reasons,
   concrete numbers) rather than vague restatements, with confidence scores
   that tracked how directly each fact was stated in context.
5. **The vault's namespace index was more useful to skim than expected.**
   Grouping by kind, newest first, made 57 memories easy to scan in a way
   `memsub audit --recent` (text-only, event-log-oriented) does not
   currently offer.
