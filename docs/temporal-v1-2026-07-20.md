# Temporal upgrade v1 (2026-07-20)

Ordered directly: "do the temporal upgrade," strict limit frugality, execute
without pausing for approval. Design sources credited below; full assumption
list and success criteria recorded before coding in WORKLOG.md's 2026-07-20
entry.

## Design

Two prior artifacts motivated this build:

- `docs/research-salvage-2026-07-20.md`: TSM (arXiv:2601.07468) builds
  semantic timelines and consolidates into durative memory units, and
  incorporates temporal intent at retrieval time (+12.2% on LoCoMo/
  LongMemEval in the paper's own report); REMem (arXiv:2602.13530) indexes
  memory with time-qualified triples (point_in_time/start_time/end_time);
  Zep (arXiv:2501.13956) uses a bi-temporal knowledge graph.
- `docs/locomo-frontier-v2-2026-07-18.md`: memsub's temporal category scored
  30.0% without session-date surfacing, 45.0% with it, on the same n=20
  holdout slice used again here -- a display-only fix (`--with-dates`,
  eval-only flag). This build is the next step: resolving relative dates
  into an actual bi-temporal valid window and using it to boost retrieval,
  not just formatting what's already retrieved.

Implementation, all opt-in and additive (default paths byte-identical,
verified by full regression suite):

1. **Bi-temporal fields** (`memsub/store.py`): `valid_from`/`valid_to` REAL
   columns, additive migration, new `Episode` fields (default `None`).
   `memsub/temporal.py` (new module): pure-Python absolute date parsing
   ("8 May 2023", "May 2023") and a fixed relative-date grammar (yesterday/
   tomorrow/today, N days/weeks/months ago, in N days/weeks/months,
   next/last week/month/year, last/next `<Month>`), all stdlib
   `datetime`/`calendar` arithmetic, zero cost. A relative expression that
   IS detected (a marker word present) but doesn't fit the fixed grammar
   escalates to exactly one qwen3:8b call, cached per (text, reference date).
   `memsub/consolidate.py`'s contradiction-supersede now closes the loser's
   `valid_to` at the winner's `valid_from`, but only when both sides already
   carry temporal scope -- a data-gated no-op on the default path, since
   nothing populates `valid_from` unless `memsub.temporal.annotate_episodes`
   is explicitly called upstream.
2. **Query-time temporal intent** (`memsub/temporal.py::classify_intent`):
   `point_in_time | range | ordinal | current_state | atemporal`, decided by
   keyword rules; one qwen3:8b escalation only when a temporal marker is
   present but the rules can't decide the sub-type.
3. **Temporal-aware retrieval** (`memsub/hybrid.py`): new opt-in methods
   `rank_temporal`/`search_temporal` and
   `rank_decomposed_graph_temporal`/`search_decomposed_graph_temporal`,
   mirroring the existing `rank_graph`/`rank_decomposed_graph` pattern --
   `rank()` and `rank_decomposed_graph()` themselves are never touched. For
   point_in_time/range intents, an episode's valid window (or session_date
   fallback) matching the query's resolved target date is folded in as one
   more RRF-fused ranking signal. For ordinal intents, the base candidates
   are re-sorted chronologically (earliest/latest per the query's wording)
   instead. Composes with `with_dates=True` context formatting
   (`memsub.store.format_episode`) unchanged.
4. **Tests** (`tests/test_temporal.py`, 44 new): migration, a dozen-plus-case
   date-resolution table, intent classification per intent (plus one
   ambiguous LLM-escalation case), boost correctness, ordinal reordering,
   contradiction-`valid_to`, and an explicit default-path byte-identical
   regression test.

### A design bug found and fixed during dev-slice iteration (see WORKLOG.md)

The first dev-slice run showed temporal retrieval *losing* to the baseline.
Two root causes, both fixed before trusting any number:

1. `classify_intent` escalated bare "When did X happen?" (LOCOMO's dominant
   temporal-question phrasing) to the qwen3:8b ambiguous fallback, which
   sometimes misclassified it as `ordinal` -- ordinal always re-sorts
   candidates by raw timestamp, which corrupts relevance for a plain
   point-in-time question with no actual ordinal signal. Fixed: bare "when"
   (after ordinal/range/current_state rules already had first look) now
   resolves to `point_in_time` by rule, zero LLM calls, both cheaper and
   safer (point_in_time degrades to a no-op when the query has no
   resolvable date; ordinal never does).
2. The eval scripts compared "baseline" and "temporal" by calling
   `rank_decomposed_graph` independently for each condition -- but its one
   decompose LLM call is not deterministic (local-model sampling varies run
   to run), so the two conditions were sometimes seeing genuinely different
   decompositions, not an isolated temporal variable. Fixed: `rank_temporal`
   and `rank_decomposed_graph_temporal` gained an optional `base_order`
   parameter so a caller can hold the base ranking fixed across both
   conditions; both eval scripts compute it once per question and reuse it.

A third, purely eval-side issue (not a library bug): `metrics_local.
ANSWER_SYSTEM`'s conservative phrasing produced verbose "this is inferred
from..." answers in some conditions, which token-F1's precision term
penalizes even when the underlying date is correct. Fixed with a stricter,
eval-local terse-answer prompt (`scripts/temporal_dev_eval.ANSWER_SYSTEM`),
same pattern as `docs/locomo-frontier-v2-2026-07-18.md` Task 2's
`ANSWER_SYSTEM_BEST_EFFORT` -- `metrics_local.ANSWER_SYSTEM` itself is
unchanged.

## Numbers

### Dev-slice (token-F1, no judge, local qwen3:8b answerer, n=30 paired)

LOCOMO dev conversations (`convs[:3]`, never the holdout split),
temporal-category (2) questions, `graph_decompose` + `with_dates=True`,
budget 2000. `results/temporal-dev-eval-2026-07-20.jsonl`.

| condition | n | mean token-F1 |
|---|---|---|
| baseline (graph_decompose + dates) | 30 | 0.4507 |
| temporal (+ rank_decomposed_graph_temporal) | 30 | **0.4571** |

Temporal beats baseline: **+0.0064 absolute (~+1.4% relative)**. Modest, not
overstated here -- this is what cleared the task's "iterate cheaply until it
beats the with-dates baseline" gate before spending any judge calls.

### Holdout, judged (n=20, the single judged comparison)

LOCOMO holdout (conversations 4-10, same seed-123 sampling protocol as every
other J-score run in this repo), temporal-category (2) only, same
`graph_decompose` + `with_dates=True`, budget 2000, local qwen3:8b answerer
for both conditions. Judge: Sonnet via `claude` CLI (subscription, no API
key), blind to condition. `results/temporal-v1-2026-07-20.jsonl`.

| condition | n | accuracy |
|---|---|---|
| baseline (graph_decompose + dates, budget 2000) | 20 | 30.0% |
| temporal (+ temporal retrieval) | 20 | 30.0% |

**Exact tie.** Per-question: 16/20 questions had the identical verdict in
both conditions; 2 flipped from incorrect to correct under temporal
("When was Deborah in Bali?", "When did Jolene's mom gift her a pendant?"),
and 2 flipped the other way ("When did Evan have his sudden heart
palpitation incident...", "When did Nate win his fourth video game
tournament?") -- the gains and losses cancel exactly at this sample size.

Sonnet CLI calls used: **40** (20 baseline + 20 temporal judge calls, all
`judge_status: "ok"`, zero retries needed). No other cloud calls anywhere in
this task -- retrieval-side decompose calls and both conditions' answering
stayed on local qwen3:8b throughout, including the dev-slice runs (0 Sonnet
calls there).

## Honest verdict

The temporal-aware retrieval layer is real, tested (44 new tests, 383 total,
all passing), additive, and shows a small, genuine improvement on the cheap
dev-slice signal (token-F1) once two real design bugs (a common-phrasing
intent misclassification, and a non-deterministic-decompose eval-comparison
flaw) were found and fixed. **It does not move the needle on the single
judged n=20 holdout slice** -- both conditions land at exactly 30.0%
accuracy, with individual question-level gains and losses cancelling out.
n=20 with a binary per-question judge has a wide enough margin of error that
a ~1-2pp true effect (consistent with the dev-slice's F1 delta) would not be
expected to show up reliably at this sample size; this result neither
confirms nor refutes a real underlying improvement, it just does not
demonstrate one at this n. `docs/locomo-frontier-v2-2026-07-18.md`'s original
30% -> 45% "with dates" finding used the SAME n=20 temporal slice and DID
show a large, clear jump -- that comparison (raw date surfacing vs. nothing)
had a much bigger effect size than this one (temporal retrieval on top of an
already-dated baseline), which is the more apples-to-apples read: the easy,
big win (surface the date at all) was already banked; this build targets the
harder, smaller remaining slice (using the date to *rank*, not just
display), and at n=20 that smaller effect isn't visible above the noise
floor.

**Say**: "The temporal retrieval layer is shipped, tested, and additive
(opt-in, default paths unchanged); on a cheap n=30 dev-slice token-F1 check
it shows a small (+1.4% relative) improvement over the with-dates baseline,
but the one judged n=20 holdout comparison came back an exact tie (30.0%
both conditions) -- not evidence it helps at that sample size, though not
evidence it hurts either."

**Do not say**: "the temporal upgrade improves LOCOMO temporal-category
accuracy" (the only judged evidence is a tie) or conflate this result with
`docs/locomo-frontier-v2-2026-07-18.md`'s 30%->45% date-surfacing finding
(different comparison, much larger effect, already shipped as
`--with-dates`, which both conditions in this round already use as their
shared baseline).

## What would be needed to know more

A larger judged n (the full n=80 slice, or the temporal category across
multiple holdout re-samples) would be needed to distinguish a genuine small
effect from noise at n=20 -- out of scope here per the task's hard sonnet-
call budget (~40 total, already spent). The dev-slice signal (token-F1,
free, local) is directionally positive and available for continued cheap
iteration without spending any further judge calls.
