# Loops v1: dropped-work detection for AI agent sessions (2026-07-22)

Built directly from a research pass on 2026-07-22 into how Claude Code
sessions die without a clean end: dangling tool calls, a scheduled
overnight wakeup that never fires, and auth/usage-limit crashes. v0 already
had one signal (a session that ends on an unanswered human ask,
`memsub/loops.py`'s `find_open_loops`/`OpenLoop`, 2026-07-21 night -- found
16 dead sessions and one lost ask that day). v1 adds four more detectors on
top of it, a unified `Finding`/`scan_loops()` API, `memsub loops
scan`/`json` CLI commands, and a `/loops` inbox page in `vault_serve.py`.

Heuristics only. No LLM call anywhere in this pass (see "does NOT do"
below for the deferred ask-extraction pass).

## Signals implemented

| # | Signal | Function | Confidence | Severity |
|---|---|---|---|---|
| 1 | Dangling `tool_use` (no matching `tool_result` anywhere later in the file) | `_detect_dangling_tool_use` | `certain` (pure structural JSON scan) | `ambient` |
| 2 | `ScheduleWakeup` never resurfaced (anthropics/claude-code #61735, open bug: the wakeup timer is in-memory only) | `_detect_wakeup_never_fired` | `likely` (absence-based inference, not proof) | `ambient` |
| 3 | Auth/usage-limit death: session's last turn is an API error, nothing after it | `_detect_auth_limit_death` | `certain` when the structured `isApiErrorMessage`/`error` fields are present; `likely` on the text-pattern fallback (older transcript shapes) | `interrupt` |
| 4 | (v0, wrapped) Unanswered explicit ask: last substantive message is the human's | `find_open_loops` / `scan_session`'s reuse of `_last_substantive` | `certain` | `interrupt` |

Confidence semantics used throughout: `certain` = a structural fact directly
present in the JSON (a field value, an id that's provably unmatched);
`likely` = an inference from absence, corroborated by known upstream
behavior but not provable from the transcript alone; `uncertain` = reserved
for future weaker signals (not currently emitted by any detector).

Severity tiers: `interrupt` = an explicit user ask was left unanswered;
`ambient` = background work vanished with no ask pending; `digest` =
informational only (reserved, not currently emitted).

### Two signals from the research pass that are deliberately NOT their own Finding

- **`[Request interrupted by user]`** is a known false-positive-prone
  marker (interrupts fire on deliberate, successful stops too, not just
  crashes). `_has_interrupt_marker` scans for it but only appends a short
  corroborating note to a Finding that already exists on its own evidence
  (e.g. an auth-death Finding). It is never, by itself, reason to report a
  session as dropped work.
- **Compaction is normal, not death.** `compact_boundary` records are
  `type: "system"` and were already skipped by `_last_substantive`'s
  user/assistant type filter. The real gap was `isCompactSummary: true`
  records: these are `type: "user"` and carry the synthetic "This session
  is being continued from a previous conversation..." text Claude Code
  itself writes after auto-compaction -- without the fix, a session that
  happened to end right after a compaction would misreport that synthetic
  summary as a live human ask. `_last_substantive` now skips
  `isCompactSummary` records; `test_scan_session_ignores_compact_summary_as_last_message`
  is the regression test.

## Live smoke run (2026-07-22, this machine, read-only)

`memsub loops scan --since 7` against every `~/.claude*/projects` that
exists (`~/.claude/projects`, `~/.claude-remote/projects`) took ~4.4s and
found:

- **60 findings** total (56 `interrupt`, 4 `ambient`)
- by signal: 34 `unanswered_ask`, 22 `auth_limit_death`, 2
  `wakeup_never_fired`, 2 `dangling_tool_use`
- **29 unique sessions** by inode (see caveat below -- the raw 60 counts
  each session found under both project directories separately)

The known 2026-07-22 case (`.../-home-user/499f00b3-d387-4a50-9726-282426ae6acf.jsonl`)
was found by **both** signal 2 and signal 3, as expected:

```
2026-07-22 09:20  [certain]  session died to an auth failure (OAuth expired) with no reply after
      .../499f00b3-d387-4a50-9726-282426ae6acf.jsonl
...
2026-07-22 00:45  [likely]  wakeup scheduled for 00:45 never resurfaced (ScheduleWakeup is in-memory only)
      .../499f00b3-d387-4a50-9726-282426ae6acf.jsonl
```

That session's shape (`ScheduleWakeup` call with `delaySeconds: 1500`
around 04:20 UTC, silence through the promised 00:46 local wakeup, a human
check-in ~9 hours later, then a `Failed to authenticate: OAuth session
expired and could not be refreshed` terminal message) is reproduced as a
synthetic fixture in `tests/test_loops.py`'s
`test_scan_session_flags_wakeup_never_fired` -- the real transcript itself
was read read-only for validation and is never copied into this repo (it
contains personal data).

No personal transcript content (message text, session ids beyond the one
already-public case above, file contents) is stored anywhere in this repo;
only the aggregate counts above.

### Caveat found during the smoke run: duplicate directories double-count

`~/.claude/projects/.../499f00...jsonl` and
`~/.claude-remote/projects/.../499f00...jsonl` are the same inode (a
hardlink) on this machine, so `default_scan_dirs()` (which scans every
`~/.claude*/projects`) reports the same session twice. v1 does not dedupe
across directories by inode/content -- deliberately not fixed here since it
wasn't part of the researched signal set and a wrong dedup could hide a
genuinely different session in some other `.claude*` variant. Documented
here as a known double-count, not silently patched.

## CLI

```
memsub loops scan [--projects-dir DIR] [--since DAYS]   # triage-ordered report, interrupt tier first
memsub loops json [--projects-dir DIR] [--since DAYS]    # same findings, machine-readable
```

Default `--projects-dir`: every `~/.claude*/projects` that exists. Default
`--since`: 7 days (same default `find_open_loops` already used).

## `/loops` page (`memsub vault serve`)

Renders the same `Finding` list as an inbox: grouped by severity tier, one
reason label per row, `interrupt` tier always expanded, `ambient`/`digest`
collapsed by default in a `<details>` (passive filtering over forced
triage -- the same research rule the signal list itself came from: most
dropped work is not worth a user's active attention, only the stuck-asks
tier is). `/api/loops.json` returns the same data as JSON.

Off by default: `vault serve`/`vault serve --root` do not scan transcripts
unless `--projects-dir DIR` (repeatable) is passed, since a real-corpus
scan costs a few seconds and the existing default page load must stay
byte-identical in cost as well as content. With no `--projects-dir`,
`/loops` renders its honest empty state ("0 findings in the scanned
window").

## Does NOT do

- **No LLM ask-extraction pass.** Every signal here is a heuristic over
  raw JSONL structure (tool_use/tool_result ids, `isApiErrorMessage`,
  `ScheduleWakeup` timing, message role/type). A smarter pass that reads
  the actual *content* of a dropped ask and summarizes what's outstanding
  (rather than just "here's the last message and where it lives") is
  explicitly deferred -- it would be the first LLM call this module makes.
- **Codex (and other non-Claude-Code) sessions that crash before writing
  any transcript file at all are invisible to every signal here.** Absence
  of an artifact is a distinct, honest "cannot tell" state -- not
  "everything's fine" -- and v1 does not attempt to detect it (there is
  nothing on disk to scan). Left for a future pass that would need an
  out-of-band heartbeat or process-liveness check, not a transcript scan.
- **The interrupted-marker signal is corroboration-only, never standalone**
  (see above) -- a session that was cleanly, deliberately interrupted by
  the human and never resumed will not be flagged by that marker alone,
  by design, because the research showed that marker fires on both
  deliberate stops and real crashes and can't tell them apart on its own.
- **No cross-directory dedup** (see the caveat above): the same session
  hardlinked/mirrored under two `~/.claude*/projects` variants is reported
  twice.
- **No automatic remediation.** Every command here is read-only: nothing
  resumes a session, retries a tool call, or answers a stranded ask on the
  user's behalf.
