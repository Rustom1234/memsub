# Garden v1: a publishable digital-garden export from a memory vault

`memsub garden` (`memsub/garden.py`) turns a subset of a vault into a static,
stdlib-only HTML site under `<vault>/garden-site/` (or `--out DIR`) that is
safe to hand to a stranger. No deploy, no hosting, no network calls anywhere
in this module -- it only ever reads from `--vault` and writes to `--out`.

2026-07-22 research pass, the gap this fills: AI-vault generators (memsub
included, before this) stop at local markdown; garden publishers (Quartz,
Obsidian Publish) start from hand-written notes and assume every note is
fair game to publish unless denylisted. Neither assumes the notes were
machine-written from a private transcript. This module is the missing
middle: an **allowlist**, not a denylist, plus a PII pass, because the
starting posture for machine-extracted memories has to be "nothing is public
by default," not "everything is public until flagged private."

## The trust model

Five rules, each fail-closed (tested: every rule has a test proving its
*failure* mode fails closed, not just its success path -- see
`tests/test_garden.py`).

1. **Allowlist, never denylist.** A note is published only with explicit
   `publish: true` frontmatter (Quartz's ExplicitPublish semantics). A note
   with no `publish` key, or `publish: false`, is never even wrapped in a
   `GardenNote` -- `resolve_publish_set()` skips it on the first check, so
   there is no downstream code path that could accidentally surface it.

2. **Asset leak guard.** A non-markdown file (`![alt](path)`/`[text](path)`)
   referenced by a *published* note is copied to the output only if the
   reference resolves to a real file under the vault root (path traversal,
   e.g. `../../secret.txt`, is rejected the same way `vault_serve.safe_path`
   rejects it). Every other file on disk -- including one sitting right next
   to a published note -- is excluded. This is a documented Quartz gap
   (unfiltered assets leak via guessable URLs); garden v1 closes it by
   requiring an actual reference, not just co-location.

3. **No silent publish.** `garden build` writes only to the local output
   directory it's told to and prints a review summary; it never deploys,
   never crons, never touches the network. A content-hash manifest at
   `<vault>/garden.json` records the last-*reviewed* publish set. If the
   current publish set has an addition or a content change `garden review`
   has not seen, `build` refuses (prints the diff, exits nonzero, writes
   nothing) unless `--yes` is passed. `--yes` publishes anyway and also
   records that set as reviewed (so the next build, unchanged, is clean).

4. **PII pass blocks, it does not scrub.** Every note about to enter the
   publish set is scanned (regex heuristics: email, phone number, IP
   address, API-key-shaped tokens, `password:`/`secret:`/`token:`-style
   credential strings) against its own `## Content` prose. A hit excludes
   *that one note* from the build and is reported by name and finding
   (`garden status`); the rest of the publish set is unaffected. Automated
   rewriting is deliberately not implemented: the block, plus a human
   looking at that note again, is the whole design. See "Does NOT do" for
   why this is a heuristic, not a guarantee.

5. **Garden norms mapped from provenance channel**, not from any
   content-based signal (the same reasoning `memsub/provenance.py` uses:
   content can lie about itself, the write-time channel tag cannot).

   | channel (frontmatter) | `human_confirmed` | garden stage | badge | extra gate |
   |---|---|---|---|---|
   | `user_stated` | any | evergreen | verified | none |
   | anything else | `true` | evergreen | verified | none |
   | `llm_inferred` | any | seedling | inferred, unverified | requires `publish_inferred: true`, else `inferred_awaiting_flag` (not published) |
   | `imported` / missing | not `true` | evergreen | *(no badge)* | none |

   The last row is this module's own judgment call, not stated verbatim in
   the design brief: the brief names two explicit buckets (`user_stated`/
   `human_verified` -> evergreen+verified, `llm_inferred` -> seedling). It
   does not say what an `imported`-channel or channel-less note (both real,
   both seen in `demo/vault`) should render as. Blocking it entirely would
   contradict rule 1 (allowlist already covers the risk: it's only in the
   set at all because a human set `publish: true` on it); rendering it
   "seedling/unverified" would misrepresent an imported observed fact as an
   LLM guess. So it renders evergreen with no verified badge -- published,
   unbadged, honest about the fact that no channel-based verification claim
   is being made for it either way.

   `Planted` = the memory's own `ts` (frontmatter `created`, or looked up
   live via `--db` when given). `Last tended` = the latest event ts for
   that memory id from the store when `--db` is given, else frontmatter
   `last_updated`.

## Stable URLs

`/notes/<id-prefix>.html`, where `id-prefix` is the first 8 hex chars of the
memory's own `id` (the same suffix `memsub/vault.py`'s `note_filename`
already uses), never a slug of the title or content. Renaming the note's
title, or rewriting its content sentence, does not move its URL --
`tests/test_garden.py::test_stable_url_survives_a_title_change` pins this. A
note with no `id` frontmatter field (a hand-authored page, or one of
`demo/vault/topics/*.md`) falls back to a hash of its relpath instead, still
independent of its title.

## What a build produces

```
<out>/
  garden.css
  index.html            # published notes grouped by `kind` frontmatter
  notes/<id-prefix>.html  # one per published note
  assets/<relpath>...    # only assets an actual published note referenced
```

Wikilinks resolve only within the published set: a `[[target]]` pointing at
an unpublished note (or one that doesn't exist at all) renders as plain text
marked "private, not published" -- never a dead link with the target's own
slug hinting at what it might be, and never a link that resolves once the
target happens to get published later without a rebuild. Each note page has
a "Linked from" backlinks section, computed the same way (published-set-only
wikilink resolution) and covered by
`tests/test_garden.py::test_backlinks_computed_within_published_set`.

Only a note's `## Content` section is rendered (or its full body when there
is no such section, e.g. a topics page) -- never the `## Provenance` /
`### Audit events` / `## Links` sections `memsub/vault.py` also writes
underneath it. Those carry run/session ids, an HMAC channel signature, audit
timestamps, and algorithmic "shares entity" cross-links: internal
bookkeeping, not something a public reader should see, and not something
the PII heuristic is designed to catch either (it isn't PII, it's just
noise `vault_serve.py` already collapses into a closed `<details>` block for
the served-vault case; garden v1's answer for a *published* export is to
simply not emit it at all).

## CLI

```bash
memsub garden status --vault ~/memsub-vault
#   published: 7
#   eligible, blocked by PII: 1
#   inferred, awaiting publish_inferred flag: 2

memsub garden review --vault ~/memsub-vault
#   + <relpath>   (new since last review)
#   ~ <relpath>   (content changed since last review)
#   - <relpath>   (no longer publish: true)
#   N note(s) approved for publish -> <vault>/garden.json

memsub garden build --vault ~/memsub-vault [--out DIR] [--yes]
#   N note(s) published, M asset(s) copied, ... -> <out>
```

`--db PATH` is accepted by all three subcommands for store-backed
planted/last-tended dates; it is optional and best-effort (falls back to
frontmatter silently if the path is missing, mirroring `vault serve`'s own
`--db` fallback contract).

## Does NOT do (v1 scope, honestly)

- **No deploy, no hosting.** `garden build` writes a local directory. Open
  `<out>/index.html` in a browser yourself, or serve it with any static
  file server of your choosing -- this module never picks one for you and
  never pushes anywhere.
- **No Quartz export.** Quartz interop (its content-graph JSON, its
  frontmatter conventions beyond `publish: true`) is explicitly deferred, not
  built. If Quartz's richer graph/search UI is ever wanted, it's a future
  `garden export --format quartz` command layered on top of the same
  publish-set resolution -- not a v1 requirement.
- **PII scanning is heuristic, not a guarantee.** Regex-based email/phone/
  IP/API-key/credential-string matching catches the common, obvious shapes
  and nothing else. It will not catch a phone number written out in words,
  a name that happens to also be someone's real full legal name, a
  screenshot embedded as an asset with text baked into the pixels, or any
  PII shape not in the pattern list. It is a second pair of eyes, not a
  substitute for the human review `garden review`'s diff exists to prompt.
- **No incremental builds.** Every `garden build` re-renders every published
  note from scratch (cheap: ~150 notes in well under a second, see the
  demo-vault end-to-end run below). There is no cache, no "only changed
  notes" mode. `garden.json`'s content hashes exist for the review gate,
  not as a build cache.
- **No topic-page grouping (yet).** The index groups published notes by
  `kind` frontmatter (fact/decision/idea/milestone/...), not by
  `demo/vault/topics/*.md` membership. Grouping by a vault's real topic
  pages would require the topic page itself to also independently clear the
  publish allowlist (or reading its (possibly unpublished) title as a
  group label, which is its own small trust question) -- deferred rather
  than decided under time pressure. `kind` is zero-risk (already part of
  the note being published) and deterministic.
- **No cron, no watch mode, no auto-publish on vault change.** Every build
  is an explicit, one-shot command a human ran.

## End-to-end run (demo/vault, tmp copy only)

`demo/vault` (the fictional persona Arjun Mehta, public-safe by
construction) itself is never modified. Verification copied it to a `/tmp`
scratch dir, hand-flagged 7 notes `publish: true` in that copy (never
committed, never touching the real `demo/vault/` in this repo), then ran the
full `status` -> `review` -> `build` cycle:

```
published: 7
eligible, blocked by PII: 0
inferred, awaiting publish_inferred flag: 0

garden build --vault vault --out site
  7 note(s) published, 0 asset(s) copied, 0 blocked by PII, 0 inferred awaiting flag -> site
  wall time: ~0.13s
```

Verified by reading the generated HTML directly: the note that had a real
wikilink to another published note rendered a working link plus a "Linked
from" backlink on the target page; wikilinks to any of the ~140 unpublished
notes rendered as plain text marked "private, not published"; the index
page grouped the 7 notes under their `kind` (`fact`/`idea`); a separate
check publishing one of `demo/vault/topics/*.md` (which has real inline
`## Key facts` bullets with `[[wikilinks]]`, unlike an individual memory
note) confirmed the same private/resolved-link behavior holds for a
richer, multi-section page too, and that the topic page's own
`<!-- memsub:distill:begin/end -->` bookkeeping markers do not leak into the
rendered output.
