# Dogfood 2, 2026-07-12: batch extract at scale + the annotate loop end to end

Acceptance run for round 2 of the Obsidian layer (bead memory-sublayer-3qv):
batch-extract a larger sample of Rustom's real Claude Code transcripts into
the same store and vault round 1 used, then exercise the new annotate loop
(`memsub vault apply`) with real corrections the way a human reviewer would
make them. All numbers are from the actual run (logs in
`/tmp/dogfood2_extract.log`, `/tmp/dogfood2_consolidate.log`); nothing is
estimated except where explicitly labeled an extrapolation.

Per the same data rule as round 1, this doc does not quote extracted memory
content or vault note filenames; memory ids and aggregate counts only.

## Corpus and sampling

`/home/user/.claude/projects/` at run time: 3,594 `.jsonl` session
files, 483MB, 25 project directories (round 1 saw 3,569/479MB/24; the
corpus grew in the hours between runs, including from round 1's own
sessions, which is itself a finding: this corpus is a moving target).

Sampling: from a size-filtered pool of 2,748 candidates (2KB-1.5MB,
excluding `subagents/` and `tool-results/` subpaths), 700 files were
scanned for real (`user`/`assistant`) turn counts with memsub's own
`load_transcript`; median 2 real turns, same as round 1. 35 files were
picked: every substantive session found (>=2 turns at pick time), capped at
4 per project directory, spanning 11 project directories, 509 real turns
total, per-file range 2-58 turns.

## The min-turns default was wrong, and got fixed mid-round

Round 1 flagged "no batch extract" as friction and this round built it with
a `--min-turns` filter, initially defaulted to 2 on the round-1 belief that
2 turns marked the automation floor. A dedicated 500-file scan (full pool,
no size filter) run before the extraction showed the belief was off by one:

- exactly 2 real turns: 466 of 500 (93.2%)
- 3 turns: 3; 4 turns: 1; 5 or more: 30
- fewer than 2: 0

2 IS the single-shot automation shape (one user message, one reply), so a
default of 2 filtered nothing. The default shipped as 3 (commit dbf0329),
and the run below used it: of the 35 sampled files, the 18 with exactly 2
turns were all skipped by the filter in under a second total, which is the
filter doing precisely its job on real data.

## Annotate loop, end to end on real memories

Three edits were made to real notes in the live vault, by hand, exactly as
a reviewer in Obsidian would, then `memsub vault apply` ran once.

1. **Correction (id 0054af99 -> bc7731e1).** An extracted skills-list
   memory attributed a tool to Rustom that his own global config explicitly
   flags as never-his (OpenClaw), at extractor confidence 1.0. The body
   text was edited to drop the wrong term. Apply superseded the old episode
   (`reason: human_correction`, `by:` the new id) and wrote a new active
   episode with provenance `origin: human_correction`,
   `corrected_from: 0054af99...`, `human_verified: true`, `confidence: 1.0`.
   Because the new episode is not an inference, the existing
   observed-beats-inferred rule ranks it above agent inferences with no new
   code (unit-tested against a newer contradicting inference; the inference
   loses).
2. **Rejection (id 70024eb7).** The extractor had stored a verbatim
   question the user asked as a `kind: fact` memory at confidence 0.95; a
   question is not a durable memory. `verdict: reject` was set in the
   note's frontmatter. Apply logged `forgotten` with
   `reason: human_reject`; the episode left the active set, row and audit
   trail intact.
3. **Confirm (id e4be2f09).** A stable, correct infrastructure fact (the
   host machine's identity) was pinned with `verdict: confirm`. Apply
   logged a `confirmed` event; the episode stays active and the decay phase
   now skips it unconditionally (decay could not be triggered live since
   nothing is 14 days old; the protection is unit-tested with a 90-day-old
   low-value memory that decay forgets without the event and spares with
   it).

All three were then verified three ways: `memsub audit <id>` showed the
expected event and provenance on each; the post-apply sync rewrote exactly
the affected notes (old correction note now `status: superseded` with a
forward wikilink to the new note, rejected note `status: forgotten`,
confirmed note gained `human_confirmed: true` and lost its `verdict` line
since sync writes canonical content); and the convergence checks passed: a
second sync touched zero files and a second apply applied zero actions
(the three now-inactive episodes are reported as skipped, by design). The
loop is loss-free: nothing a human did was overwritten before being
captured, and nothing was applied twice.

One bug was found and fixed during this exercise (commit b7ae711):
re-running apply before a resync would have logged a duplicate `confirmed`
event on a pinned note. Harmless for decay protection but audit-trail
noise; apply now treats an already-confirmed note as unchanged.

## UX friction and honest findings

1. **Extraction confidence is not a review signal.** The two memories a
   human had to fix carried confidence 1.0 and 0.95, the highest values in
   their files. Confidence tracked how directly the transcript stated the
   claim, not whether the claim belongs in memory, so it cannot gate an
   auto-accept path. This strengthens the case for the annotate loop being
   the product surface rather than an afterthought.
2. **No resume for batch extract.** The first extract invocation was
   killed at 120s (foreground timeout) after finishing 1 of 35 files.
   Resuming meant manually diffing the store's recorded source paths
   against the sample list to rebuild the remainder, because re-running the
   same command would have re-extracted the finished file and duplicated
   its memories (consolidation's dedup would likely catch most, but that is
   cleanup, not prevention). At full-corpus scale (hours of wall time) this
   is the top missing feature: skip files whose path already appears as a
   source in the store, or an explicit `--resume`.
3. **Full-corpus extrapolation (labeled estimate, not measured).** From the
   measured rates (6.8% of 500 scanned sessions have >=3 turns; ~37s per
   processed file; skips are sub-second), extracting the whole 2,748-file
   candidate pool would process on the order of 190 files in roughly 2
   hours on qwen3:8b. Feasible overnight, untested.
4. **content_hash migration churn.** The first sync after this round
   rewrote all 57 round-1 notes solely to add the new frontmatter field.
   One-time and correct, but on a large pre-existing vault it would look
   like a mass edit to any file watcher or sync tool pointed at the vault.
5. **Apply-before-sync staleness reads as alarming.** Apply reported
   `skip inactive` for a note whose file still said `status: active`,
   because consolidation had superseded the episode after the previous
   sync. Correct behavior (the note file is just stale), but the first
   read of that output line suggests something is wrong. Workflow rule
   that falls out: run `vault sync` immediately before a review session.
6. **The verdict field is hand-typed.** Obsidian's properties UI renders
   frontmatter as editable key/value pairs, which is workable, but the
   reviewer has to remember the two magic strings (`reject`, `confirm`).
   A note template or checkbox-style property would remove that; not
   built this round.
7. **Positive: correction is the cheapest of the three gestures.** Editing
   the body text in place, with no frontmatter at all, is the most natural
   Obsidian action and maps to the richest store outcome (supersede with
   human-verified provenance). The design choice to make plain text editing
   the correction mechanism, rather than a special field, was validated by
   actually doing it.
