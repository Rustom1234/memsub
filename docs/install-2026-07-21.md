# One-line install

    bash scripts/install.sh

That's it. It is portable (no hardcoded paths -- everything derives from
`$HOME` and the script's own location) and idempotent (safe to run more
than once; every step checks "already done" before doing anything).

## What it does

1. Checks `python3.10+` and a local `ollama` daemon. Neither check is a
   hard requirement to *finish* the install (see "Degraded modes" below);
   python3.10+ is the one true hard requirement (nothing else can run
   without it).
2. Creates a virtualenv in this repo (`.venv/`) and `pip install -e .`
   into it. Prefers `uv venv` / `uv pip install` when `uv` is on `PATH`
   (faster, and does not depend on the system's `ensurepip`/
   `python3-venv` package being installed -- a common gap on minimal
   machines and containers), falling back to the stdlib `venv` module
   otherwise.
3. Initializes the memory store (`~/.memsub/memory.db` by default) and
   the vault directory (`~/memsub-vault` by default).
4. Installs the extraction/consolidation/vault-sync cron jobs and the
   Claude Code recall hook, idempotently.
5. Prints the "voila" next steps: the command to start the UI, and the
   URLs to open.

## Overridable via environment variable

All optional; sane defaults if unset.

| Variable | Default | Meaning |
|---|---|---|
| `MEMSUB_DB` | `$HOME/.memsub/memory.db` | SQLite store path |
| `MEMSUB_VAULT_DIR` | `$HOME/memsub-vault` | vault folder |
| `MEMSUB_NAMESPACE` | `claude-code` | extraction namespace |
| `CLAUDE_SETTINGS` | `$HOME/.claude/settings.json` | Claude Code settings file the hook is written into |
| `CRONTAB_CMD` | `crontab` | crontab binary/wrapper (override for tests -- see below) |

## Degraded modes (never a hard failure on an optional dependency)

- **`python3` missing, or older than 3.10**: aborts. Nothing else in this
  script can run without it.
- **`ollama` missing**: the venv, store, vault, cron jobs, and hook are
  still installed in full. Every LLM-backed feature (extract, consolidate,
  `/ask`, idea resonance's bridge text) reports a clear "ollama not
  reachable" message at call time until you install ollama and pull
  `qwen3:8b`. No re-install is needed afterward -- readiness is checked
  when the feature runs, not when this script runs.
- **`jq` missing**: the Claude Code recall hook step is skipped with a
  clear message (jq is needed to safely merge into an existing
  `settings.json` without clobbering unrelated hooks); everything else
  still installs.

## What is *not* ported from `~/scripts/install-durable-capture.sh`

The original personal installer also wires a separate transcript-capture
layer (`~/scripts/memsub-inbox.sh` / `memsub-inbox-sweep.sh`, a
`SessionEnd`/`PreCompact` hook) that lives outside this repo, on one
specific machine. Porting it here would either silently fail on any other
machine (the referenced script would not exist) or require inventing a
new personal-glue layer that is not part of the memsub product. Only what
is genuinely shippable from this repo is installed:

- the extraction/consolidate/vault-sync cron job
  (`scripts/daily_extract.sh`)
- the vault-apply cron job (`memsub vault apply`)
- the repo rollback watchdog (`scripts/repo_watchdog.sh`, scoped to just
  this repo via `REPO_WATCHDOG_REPOS`, not the original's hardcoded
  two-repo list)
- the `UserPromptSubmit` recall hook (`scripts/memsub-recall-hook.sh`)

## Voila: what you get

```
Start the UI:
  <repo>/.venv/bin/memsub vault --db "<db>" serve --vault "<vault>" --port 8766

Then open:
  http://127.0.0.1:8766/           dashboard
  http://127.0.0.1:8766/ask        ask your brain, with citations
  http://127.0.0.1:8766/resonate   drop an idea, find what it connects to
  http://127.0.0.1:8766/graph      the knowledge graph, laid out by meaning
```

From there it keeps building itself: the cron jobs extract new sessions
every 30 minutes, consolidate (dedup, prune stale memories, resolve
contradictions) and sync the vault every 10 minutes, and every prompt you
type gets a silent recall check against what is already there.

## How this was tested

No real system changes: run against a temporary copy of the repo (so venv
creation and `pip install -e .` never touch the real checked-out repo's
working `.venv`), with `HOME` pointed at a throwaway sandbox directory and
`crontab` replaced by a script that appends to a local state file instead
of touching the real user crontab (`CRONTAB_CMD` override). Verified:

- a fresh run creates the venv, the store (a valid SQLite file), the
  vault directory, three cron lines in the fake crontab state, and the
  hook in the fake `settings.json`, then exits 0.
- a second run reports every step as "already exists" / "already
  present" and adds nothing new (true idempotency, not just "doesn't
  crash").
- with `ollama` removed from `PATH`, the run still completes and installs
  everything else, printing the degraded-mode note instead of failing.
- the real crontab (`crontab -l`), the real `~/.claude/settings.json`,
  and the real repo's working `.venv` were all confirmed byte-for-byte
  unaffected (grepped for the sandbox's own tmp path, zero matches; the
  real `.venv/bin/python` still resolves to the pre-existing
  interpreter).
