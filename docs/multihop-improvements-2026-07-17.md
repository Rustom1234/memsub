# Multi-hop improvements measurement (2026-07-17)

Measures the two Part B items from docs/improvement-plan-2026-07-17.md (write-time fact
fusion, bounded query-time decomposition) against the LOCOMO dev slice (conversations
1-3, budget 1000), the same split and metric family (evidence-all / evidence-any) as
docs/error-analysis-locomo.md and docs/benchmark.md's dev-eval log.

Generated by `scripts/multihop_improvements_eval.py` on 2026-07-17, qwen3:8b via ollama
(think disabled for speed, see memsub/backends.py), wall time ~150s for the full run
across all three conditions. Raw per-question and per-condition summary records:
results/multihop-improvements-2026-07-17.json (JSONL, one line per record).

## Baseline correction

The eval first reproduces the shipped hybrid v2 default exactly (dense_weight=0.5,
bm25_weight=1.0, temporal=True, speaker_boost=1.0, session_weight=3.0, the frozen
params from docs/benchmark.md's "Frozen stack after dev selection" section) rather than
`memsub.bench.HybridSystem`'s bare "benchmark-era, all boosts off" defaults, which
produce a materially weaker (59.5% / 73.6% total) baseline that is not what ships. The
baseline row below matches docs/benchmark.md's documented dev totals exactly (72.8% /
85.1%, multi-hop 20.3% / 77.0%), confirming the harness is measuring the real shipped
retriever before any delta is trusted.

## Reading the numbers, honestly

Neither intervention improved multi-hop evidence recall on this dev slice. Both moved
it slightly the wrong way or left it flat:

- **Fusion alone regressed multi-hop evidence-any by 2.7pp** (77.0% -> 74.3%, exact
  counts 57/74 -> 55/74) and single-hop evidence-all/any by 0.5pp (87.0% -> 86.5%,
  174/200 -> 173/200). evidence-all is unchanged everywhere (20.3% multi-hop, 72.8%
  -> 72.6% total is single-hop-driven, not multi-hop-driven). Cause: the LOCOMO
  evidence-all/any metric can only credit the original annotated dia_id turns; a fused
  episode is a new synthesized entry with its own id, so it can never itself count as
  evidence. Every fused entry ingested still competes for the same 1000-token budget
  as the original turns it was built from, so on net it costs some budget-cut misses
  without ever being able to buy one back on this metric. This mirrors exactly the
  finding already on record for the "sleep" extension in docs/benchmark.md ("evidence
  recall cannot credit summary episodes"): write-time synthesis needs an
  answer-quality metric to show its value, not an evidence-membership metric.
- **Decomposition on top of fusion was a wash relative to fusion alone**: identical
  aggregate numbers (20.3% / 74.3% multi-hop, 72.6% / 84.3% total). Diffing the 383
  per-question records directly shows this is not a no-op in disguise: the decompose
  call did fire and did change retrieval order for 6/383 questions (verified against
  the JSONL records), but 3 flipped a question into a hit and 3 flipped a different
  question out, netting to exactly zero on both evidence-all and evidence-any. This
  matches the existing, already-reverted finding in docs/benchmark.md's "heuristic
  query decomposition" row: only a small minority of LOCOMO's "multi-hop" category is
  a real chainable multi-topic question (most are single-topic aggregation, e.g. "What
  activities does Melanie partake in?"), so a decomposer, heuristic or LLM-judged, has
  few real opportunities to help and about as many chances to hurt by fragmenting a
  single-topic query's own top-k signal.

## What this does and does not settle

This measures write-time fusion and query-time decomposition through the
evidence-recall lens only (matching the exact metric family that produced the 94.6%
multi-hop failure figure this work targets). It is not evidence that fusion is
worthless: MIRIX's own reported multi-hop gain comes from write-time consolidation
evaluated with an LLM-judge accuracy metric on generated answers, not turn-level
evidence-membership. The evidence-recall metric can only ever cost fusion budget, never
credit it (a fused entry contains the right information but is not the original
evidence turn) -- so the fair test needs a metric that can see fused content. That test
is below.

## Fair test: answer quality on the multi-hop slice (2026-07-17, follow-up)

Generated by `scripts/multihop_answer_quality_eval.py`. Reuses the repo's existing
answer-quality machinery unchanged (no new harness, per instructions): `ANSWER_SYSTEM`,
`BUDGET`, `FROZEN` (the frozen hybrid v2 params), and `token_f1` all imported directly
from `scripts/metrics_local.py`, the same judge-free deterministic token-F1 protocol
that produced the documented 0.152 holdout number (docs/benchmark.md), so these numbers
are internally comparable to that one. qwen3:8b is both the memory backend and the
answerer, budget 1000, no LLM judge.

**Slice**: LOCOMO dev conversations 1-3 (never holdout), category-1 (multi-hop)
questions with a non-empty gold answer, n=74. This is the full multi-hop dev slice, not
a subset: a timing check (single real answer call with real context, ~0.6-0.7s with
`think=False`) showed the full 3-condition x 74-question run would finish in a few
minutes, well inside the coordinator's ~90 minute cap, so the pre-registered
seed-2026/n>=60 fallback subset was not needed. Actual wall time: 270s. Raw per-question
records (question, gold answer, prediction, F1, exact-substring, latency):
results/multihop-answer-quality-2026-07-17.jsonl (JSONL, one record per line, streamed
and flushed as the run progressed, resumable).

| condition | n | mean token-F1 | exact-substring rate | mean answer latency (s) |
|---|---|---|---|---|
| baseline (shipped hybrid v2) | 74 | 0.1946 | 0.0676 | 0.723 |
| fusion (write-time, Task 1) | 74 | 0.1907 | 0.0676 | 0.757 |
| fusion + decompose (Task 1+2) | 74 | 0.2029 | 0.0676 | 0.788 |

### Verdict

**Fusion alone still does not help.** F1 goes from 0.1946 to 0.1907, a 2.0% relative
drop, the same direction (flat-to-negative) as the evidence-recall run. Spot-checking
individual predictions (e.g. "What is Caroline's identity?": baseline "Caroline's
identity is transgender" F1 0.286 vs fusion "Caroline identifies as a trans woman" F1
0.250) shows fusion sometimes changes phrasing without changing correctness, and
sometimes trades one budget slot for another without a clear net win. This parks the
MIRIX write-time-fusion hypothesis on real measurement, both metrics agree: fusion by
itself is not moving multi-hop quality on this dev slice.

**Fusion plus decomposition shows a modest positive delta**: F1 0.2029 vs baseline
0.1946 (+4.3% relative) and vs fusion alone 0.1907 (+6.4% relative). This flips the sign
from the evidence-recall run, where decomposition on top of fusion was an exact wash.
Read this cautiously, not as confirmation: the effect size (0.008-0.012 absolute F1) is
small at n=74 with a single run per condition (no repeated trials, no variance
estimate), so it is plausibly within single-run noise rather than a robust effect;
exact-substring rate is identical (0.0676, 5/74) across all three conditions, which is
also consistent with a small, noisy delta rather than a clear win. The honest
conclusion: the gain tracks with decomposition, not fusion (fusion alone is flat/down,
decomposition added on top is what moves the number), so if either mechanism deserves
more investment on the strength of this run, it is decomposition, not fusion. Neither
result is strong enough to override the plan's move to the graph layer (item 3 of
docs/improvement-plan-2026-07-17.md Part B) as the next real lever; this does argue for
keeping decomposition as a cheap, opt-in retrieval-time knob rather than parking it
alongside fusion.

## What is shipped regardless of this result

Both features are opt-in and off by default, exactly as scoped:

- Fusion only runs when consolidate() is called with a backend (same gate as the
  existing contradiction pass); it never deletes or hides a source memory, and it is
  idempotent (re-running against an unchanged store makes zero new LLM calls).
- Decomposition only runs when a caller explicitly calls
  `HybridRetriever.rank_decomposed` / `search_decomposed` with a backend; the default
  `rank()` / `search()` path is unchanged.

Neither is wired into a default code path by this session's work, so this negative
result on the dev slice costs nothing to ship: the audit-trail and provenance-linking
value of fusion (a real, if unmeasured-here, capability) and the bounded-cost design of
decomposition stand on their own regardless of this particular metric's verdict.
